# Project Summary — AI School Management & Analytics Platform

*Reviewed 24 August 2026. Repository: `F:\ZCodeProject`.*

## What it is

This is a full-stack school management system with an AI layer bolted onto the middle of it. A Spring Boot REST API serves a React single-page application, and behind the ordinary academic CRUD — schools, courses, enrollments, assignments, submissions, grades — sit three genuinely ambitious AI features: a natural-language-to-SQL query engine, a retrieval-augmented-generation chat assistant backed by a vector database, and a per-user configuration layer that lets each account plug in its own LLM provider and API key.

It is a solo project by Dheeraj DVN, started on 23 July 2026, with 43 commits on `main`. It is deployed and live: the frontend on Vercel, the backend on Render's free tier, with Neon serverless PostgreSQL, Upstash Redis and a Qdrant Cloud cluster behind it. A GitHub Actions cron pings the health endpoint every five minutes to stop Render's free dyno from sleeping, which tells you something useful about the hosting budget and therefore the intended audience — this reads as a portfolio piece built to demonstrate range, and on that measure it succeeds.

## The stack

The backend is Spring Boot 3.5 on **Java 17**, built with Maven, organised into the conventional controller/service/repository layering under `com.ai.dashboard`. Persistence is Spring Data JPA against PostgreSQL, with Hibernate managing the schema directly (`ddl-auto: update` in dev, `none` in prod) — there is no Flyway or Liquibase, and the lone `schema.sql` is almost certainly never executed. Redis holds refresh tokens and backs a rate-limiting filter. Authentication is stateless JWT with a refresh-token cookie, and authorisation is method-level `@PreAuthorize` across six roles. Swagger UI, Actuator with Prometheus metrics, and custom health indicators for Ollama, Qdrant and Redis round it out.

The AI layer is the interesting part. It uses **LangChain4j 0.34.0** with Ollama for local inference and `nomic-embed-text` for 768-dimension embeddings, and it adds a strategy-pattern provider registry offering nine LLM backends — Ollama, OpenAI, Anthropic, Azure OpenAI, DeepSeek, Google Gemini, Groq, Mistral and OpenRouter — selectable per user, with API keys encrypted in the database. Vector storage is Qdrant over its REST API. Document ingestion parses uploads with PDFBox and Apache POI, chunks the text at 750 words with 100 words of overlap, embeds each chunk and upserts it to Qdrant; retrieval pulls the top five hits and streams an answer back over server-sent events with source citations.

The frontend is React 18 with React Router 6, Vite 5, Bootstrap 5 plus about thirty hand-written CSS files organised as a small design system with light and dark themes, Chart.js for visualisation, and axios for HTTP. It is plain JSX throughout — no TypeScript. All 105 routes live in a single 1,803-line `App.jsx`, each page lazily imported and wrapped in three layers of guard components. There are role-specific portals for admin, school admin, principal, teacher and student, plus a marketing landing page with an animated canvas background.

## Where it is genuinely strong

The AI plumbing is more careful than the average portfolio project. The natural-language-to-SQL path does not simply hand model output to a database: `SqlValidator` parses the generated SQL with JSqlParser and rejects anything that is not a `SELECT`, checks every referenced table against a whitelist, blocks `information_schema` and `pg_*` probing, and screens for sensitive column names. Execution is then capped at 200 rows with a five-second query timeout on a read-only, forward-only cursor. That is a real defence in depth, and the layered design — parse, whitelist, cap — is the right shape.

The provider-strategy layer is clean and extensible: adding a tenth LLM vendor means writing one class. API keys are encrypted at rest with AES-GCM, masked on read, and the base-URL validator blocks cloud metadata endpoints to prevent SSRF. The SSE streaming in the RAG chat is real token streaming, not a simulated single chunk, and it includes a similarity-score floor so the assistant declines to answer rather than hallucinating when retrieval comes back weak. Error handling is centralised in a `@RestControllerAdvice` with about seventeen handlers mapping domain exceptions to sensible status codes. The documentation set — seven markdown files covering architecture, database, AI, deployment and troubleshooting, with Mermaid diagrams and screenshots — is more than most projects of this size bother with.

## Where it needs work

**The most urgent item is a privilege-escalation hole.** `PUT /api/users/{id}` is annotated `isAuthenticated()` and protected only by a self-or-admin ownership check, while `UserServiceImpl.updateUser` applies the submitted `roles` set unconditionally — and auto-creates any role name that does not already exist. A student can therefore update their own record with `roles: ["ROLE_SUPER_ADMIN"]` and promote themselves. The properly guarded `POST /users/{id}/roles` endpoint is bypassed entirely. This is a small fix and worth making before anything else.

Two related credential problems compound it. `AesEncryptionConverter` falls back to the hardcoded key `1234567890123456` when no encryption key is configured, and the README publishes that value in its environment-variable table — so by default the stored provider API keys are encrypted with a publicly known key. The README also publishes working admin credentials (`dheerajdvn` / `root@123`), and the login page ships one-click demo buttons for admin, teacher and student accounts, all with the password `password`. Anyone who loads the public login page has admin access.

**The single largest structural issue is that there are two unrelated student models.** `entity/Student` is a flat, standalone table — name, course, subject, fee, address — with no foreign keys to anything. `entity/User` plus `Role` is the real identity model, and every academic relationship (enrollment, submission, course teacher, document uploader) points at `User`. Registration creates a `User` and no corresponding `Student` row. Critically, the AI layer only knows about the flat table: the NL-to-SQL system prompt tells the model the database has "a single table named `student`", and the SQL validator whitelists `student` while deliberately excluding `users`. The practical consequence is that asking "how many students are enrolled?" through the AI returns one number while the dashboard returns a different one, because they are counting two different populations behind one product.

**A large share of the UI is not connected to the backend.** The teacher gradebook, attendance register, homework review and study materials; the entire exam module; the school profile page; and notifications all persist to `localStorage` with hardcoded rosters and stats. The gradebook even fakes a 600ms save and then reports "successfully saved and compiled". `/teacher` and `/principal` — the default landing pages for two of the five roles — are literal "Coming Soon" stubs. The student and school dashboards render hardcoded figures behind a `setTimeout`. This is the widest gap in the project: the application looks considerably more complete than it is.

There are also two live frontend bugs worth knowing about. The flagship NL-to-SQL screen almost certainly renders nothing, because `AskAiPage.jsx` unwraps the response envelope a second time after the API layer has already done it. And two axios response interceptors are attached to the same client instance with conflicting policies — the second treats a 403 like a 401, so a legitimate permission denial logs the user out instead of showing the unauthorised page. Three competing token-storage implementations coexist, one of which is dead.

**Test coverage is thinner than it appears.** There are 127 backend unit tests, which sounds reassuring, but no integration test actually executes — the `@SpringBootTest` base classes were written and never applied to anything, so nothing verifies that the application context even starts. There are no controller tests, meaning none of the `@PreAuthorize` rules are covered, which is precisely why the escalation path above went unnoticed. The JWT service, authentication filter, refresh-token service and most of the AI subsystem are untested. The JaCoCo gate is set to 15% with `haltOnFailure=false`, so it cannot fail a build. The frontend has no linter and no tests at all across roughly 25,000 lines of JSX. CI consists of the keep-alive cron and a Jenkinsfile; there is no build-and-test pipeline.

Finally, a fair amount of dead weight has accumulated: a complete STOMP-over-SockJS real-time layer (four services and four hooks) that nothing imports, `@tanstack/react-query` mounted as a provider with zero hooks actually used, around thirty unreferenced components, an entire parallel `src/api/*` client layer, five unreachable prompt templates, and residue from an abandoned Java 17-to-21 migration under `.github/modernize/`. Grading, document management and chat each exist in two parallel implementations, and CORS is configured twice.

## One caution on the repo's own documentation

`AUDIT_REPORT.md` awards the project "Overall Score: 10/10 (Production Grade)" and states that all previously identified gaps are "100% resolved". That document is promotional rather than evaluative, and it should not be relied on. The README drifts from the code in the same direction: it badges Java 21 where `pom.xml` declares 17, credits Spring AI where the code uses LangChain4j, and presents AES-128 as a deliberate feature when it is actually the result of the encryption key being silently truncated to sixteen bytes.

## Suggested order of work

Fix the role-escalation path in `updateUser` and remove the hardcoded encryption-key fallback. Strip the published credentials from the README and the demo buttons from the login page. Add role gates to `/exam/*`, `/documents` and `/assignments`. Then resolve the double-unwrap in `AskAiPage` and consolidate the two axios interceptors onto a single token store, since those are cheap fixes to visible breakage.

After that, the two decisions worth making deliberately rather than incrementally: reconcile the `Student` and `User` models, or document explicitly that the AI layer reports on a separate demo dataset; and decide for each `localStorage`-backed portal whether to wire it to the API or label it clearly as a mockup. Alongside either, add a smoke test that boots the Spring context and a handful of `@WebMvcTest` cases over the authorisation rules — that is the change that would have caught the escalation bug, and it is what makes the rest of the cleanup safe to attempt.
